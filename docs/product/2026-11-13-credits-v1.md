# StoryDate 积分与内测补贴 v1

关联：#150；依赖 #149 的账号隔离、剧情回流与用量日志。本文是可评审方案，正式扣费尚未启用。

## 产品规则

统一卖“继续和角色互动的机会”。用户看到固定点价，后台记录真实模型成本；不把 token 计价暴露给用户，也不因换供应商、模型重试、语言不同而临时加价。

| 行为 | 本轮建议价格 | 状态 |
|---|---:|---|
| 角色 / 普通故事聊天，短回复或标准回复 | 1 点 / 成功回复 | 已实现 |
| 角色 / 普通故事聊天，长回复 | 2 点 / 成功回复 | 已实现 |
| 用户主动重新生成 | 与当前回复长度同价 | 已实现；发送前明示 |
| 网络重复请求、24 小时内恢复已结算回复 | 0 点额外费用 | 已实现 |
| 打开角色页、静态剧本、存档、浏览历史 | 免费 | 保持 |
| 推荐行动 | 免费 | 收费模式使用已有本地开场选项/缓存，不额外自动调用模型 |
| 创作助手、生成封面、游戏内结构化自由发言 | 待各自报价和账号接入 | 收费模式拒绝模型调用；非收费模式保持现有行为 |

最后一行是本轮明确边界：不能把这些旧入口当成免费模型旁路，也不能让没有展示价格的功能暗扣点。全站打开正式扣费前，需要补齐这些功能的交互，或在产品入口明确暂停相应 AI 操作。静态游戏继续可玩。

现有充值包先保持：200 点 / $1.99，2,500 点 / $19.99，5,000 点 / $29.99。避免这次同时改 Stripe 商品、订阅、自动续费和付费门槛，造成无法判断哪项改变影响了转化。零售点价是试行假设，不能当作已验证的毛利。用 #149 的实际 token 成本、Firebase/支付成本、失败和备用模型成本核算后再修订；修价必须换 `PRICE_VERSION`。

## 三类余额，一套消费规则

1. **购买积分**：Stripe 已签名且金额、商品、账号、环境均匹配的订单到账。永久有效。不能靠浏览器回调加点。
2. **赠送积分**：活动、内测和签到，记录来源及有效期。不能兑换现金或转给其他账号。优先消费快到期的赠送积分。
3. **历史余额**：旧系统没有可靠地区分所有来源，完整保留，不追认成购买积分、不设有效期。排在赠送之后、购买之前消费。

钱包展示可用余额、三种来源、生成预留和最近一次赠送到期时间；记录列表展示最近 50 条，完整服务端流水单独保存。预留已经从可用余额扣除，展示“预留”不能再次相减。

旧余额在事务里懒迁移；滚动部署期间旧写入器只增加总余额而不生成 lot 的差额，保守记为历史余额，避免丢失到账。不得通过重新部署旧钱包代码来回滚；关闭扣费开关即可，保留 v2 的恢复和记账能力。

## 早期体验：补贴点数，不改正常价格

建议第一轮内测：**50 个受邀账号，每人 100 点，14 天有效，总预算 5,000 点**。这是建议配置，本次未真实发放。活动能指定单个账号，也能指定名单；用户使用同一价格消费。后续研究需要更多轮体验，另建新活动，不无限续期原活动。

活动字段：唯一 id、每人点数、固定预算、Firebase UID 白名单的散列、领取起止时间、赠送到期时间。服务端验证资格并在同一事务里扣减预算及给账号加点。活动码只是查找入口，泄露活动码不会使白名单外账号获得资格。同一账号、同一活动只到账一次；操作工具重复运行也不会重复发放。

建议收费模式签到从 100 点改为 **3 点 / 天，领取后 7 天有效**，保留轻体验而非无限替代购买。每天按上海时间零点重置。收费开关关闭时，为避免本轮偷偷修改线上行为，沿用原 100 点签到；正式启用时的变化必须向已有用户说明。

补贴**会影响**用户行为，不能天然保证“不影响后面的测试”。分开观察：

- 补贴队列：领取率、赠送消耗、故事完成、次日回访，回答产品是否吸引人。
- 到期 / 用完后的队列：愿不愿购买、购买后花多少购买积分、7 日复购，回答付费意愿。
- 历史余额用户单列，不能与全新用户混算。
- 真正收入只认 Stripe 已确认的购买，补贴点数消费不是收入；`spent.grant`、`spent.purchased`、`spent.legacy` 分开统计。
- 不因聊天内容、角色感情表达或用户脆弱状态临时改变价格。不以关系惩罚强迫充值。

## 扣账与异常

`报价 → 服务端验证身份 / 价格版本 → 原子预留 → 模型生成 → 成功结算或失败释放`。

- 用户没登录、点数不足、价格变化或钱包不可用：不调用模型，保留输入和原回复。价格来自服务端；客户端不能自报零价。
- 并发请求按事务争用同一钱包，最多 4 个预留，不得透支。Firebase 事务内只有读写，不执行模型调用或外部副作用。
- 请求编号绑定账号及完整请求的散列；同编号换内容报冲突。重复请求不重新进入模型。
- 成功回复短期缓存 24 小时，仅所属账号可恢复；长期消费凭证与临时正文分开存，流水不保存输入/输出正文。缓存过期后仍保留幂等凭证，不把旧请求再次扣点。
- 生成失败、生成中取消、空回复、截断或没有成功结束标记的回复均释放预留。途中可见文字但最终失败，也不结算。模型已成功完成后停止打字动画，会直接显示完整回复，不退还已经成功消费的点数。已完成并结算的回复不会因网络丢了最后一个事件而再次生成；使用同一请求恢复。
- 进程崩溃等导致预留未释放：10 分钟租期到后，下次查余额 / 查状态 / 操作时在事务里释放。这是懒恢复，不承诺无人访问时有定时任务自动执行。
- 预留期间赠送点数到期：释放仍按原到期时间处理，不能借失败续期。完整流水包括释放与到期，可核对回余额。
- 结算/释放数据库失败时保留幂等状态，日志标记 `credit_release_pending`；核对状态或等租期恢复，不自动新开一次消费。

## 运维、权限与隐私

- `CREDIT_BILLING_MODE` 默认 `off`。`test` 只使用 test 钱包，必须和 Stripe 模式一致。`live` 必须同时有 `VERCEL_ENV=production`、`CREDIT_LIVE_ENABLED=true`；Preview 不得碰 live 余额。无效配置拒绝生成。
- 不新增 Vercel Function。现有 `/api/wallet` 增加 `quote/status/claim`；扣账、结算均只能由生成服务执行。浏览器没有任意加点、改价、结算接口。
- Firestore 安全规则保持全部钱包、消费凭证、活动和流水为 Admin-only。活动名单文件必须是操作员的 `.local.json`，已忽略，不进入仓库。
- 短期回复集合 `replica-credit-responses-test/live` 的 `expiresAt` 是 Firestore Timestamp。托管平台启用 TTL 才会物理清理；服务端即使 TTL 延迟也不会返回过期正文。**TTL 与真实登录环境未配置前，不启动正式收费。**
- 后台运维通过既有托管环境身份运行，不下载、复制或在命令行传递密钥。仓库脚本不会打印密钥、原始 UID 或聊天正文。
- `credit-campaign.mjs` 默认 dry-run，不初始化 Firebase；`--apply` 才发放，live 还需要 `--allow-live` 和独立环境门闩。用户没有授权真实发放，本轮不运行 apply。
- `credit-audit.mjs` 是只读汇总，分开显示发放/已消费来源、可用、预留和到期；不把点数当美元收入。它不能代替按 Stripe receipt 与完整流水的财务核对。

操作示意（在已配置的托管运维环境中，文件内 `uids` 是经批准的 Firebase UID）：

```sh
node scripts/credit-campaign.mjs --file=/private/path/beta.local.json --mode=test
# 审核 dry-run 和名单后，测试发放才加 --apply；本轮未执行。
node scripts/credit-audit.mjs --mode=test
```

## 交付与启用顺序

1. 独立 PR，先依赖 #149 评审；不合并 main、不改 Vercel 配置、不发真实点数。
2. 本地模拟账号/模型验收；补测试 Firebase 登录配置后，Preview 使用 test 积分和明确获准的模型测试，跑双账号及跨设备恢复。
3. 补齐非聊天 AI 入口的报价/暂停展示，配置回复 TTL，审核充值条款、退款/拒付人工处理与自动冲正边界、价格和活动预算，再由用户决定是否启用 live。
4. 先观察一批受邀用户，不自动调整价格、不自动扩大活动预算；开启/关闭计费用同一版本开关，账本始终保留。

[回复缓存 TTL 说明](https://firebase.google.com/docs/firestore/ttl)。TTL 删除有延迟，服务端的读取过期判断不能省略。

外部工程约束参考：[Firestore 事务](https://firebase.google.com/docs/firestore/manage-data/transactions)、[Stripe 幂等请求](https://docs.stripe.com/api/idempotent_requests)。本系统的消费请求凭证不依赖 Stripe 幂等窗口，单独持久化。
