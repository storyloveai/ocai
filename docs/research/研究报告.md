# 角色 AI 网站：接入、角色控制、记忆、训练与评测

调研日期：2026-10-10。面向项目：oocai.netlify.app。当前项目仍是静态 UI 演示，尚未接入模型。本次仅研究、整理实验素材，没有购买 API、训练或更改线上应用。

这是一份覆盖代表性实现路线的资料集，不是对互联网所有平台的穷尽清单。技术结论优先依据官方文档、作者仓库、模型卡及论文；社区讨论只作为待验证假设。闭源平台公开功能不能证明其内部实现。页面抓取失败、登录后的私有内容和未公开训练集不纳入已验证材料。资料库提供原始来源链接，不镜像完整第三方文章或大模型权重。

## 先判断我们究竟在调什么

角色 AI 可以拆为五层：基础模型决定语言与推理能力；角色描述与示例控制身份和表达；记忆系统提供当前可用事实；剧情状态控制关系和行动条件；反馈与评测决定迭代方向。只改温度无法补上缺失的事实，只增加上下文也无法保证角色在冲突场景中的选择符合人设。

“调教”至少有四种不同操作：提示词与示例不修改权重；检索与摘要管理运行时信息；采样参数改变候选文本选择；SFT、LoRA、DPO 才是训练权重或适配器。聊天变熟、记住名字、评分后下一句不同，都不能单独证明平台为该用户在线微调了模型。

我的初步判断：我们的第一版应采用可替换的模型 API，加角色卡和结构化记忆，再用中文多轮盲测定位问题。是否训练、训练哪个模型，留到有失败样本以后决定。以下建议均为项目设计判断，不是对闭源平台的内部技术断言。

## 接 AI：前端之外必须有什么

SillyTavern 的文档区分 Chat Completions（消息数组）与 Text Completions（拼接文本）；这不等于云端与本地的区别。角色卡、历史、世界书最终都会变成送给模型的上下文。[1]

三条接入路线：

1. 官方厂商 API：直接使用其模型，服务端处理其请求格式、流式响应与失败重试。模型可用性和内容边界以提供方当时规则为准。
2. 聚合 API：例如 OpenRouter，便于在同一接口下比较多种模型。仍需记录真实模型和提供商，避免路由变化让实验不可复现。[30]
3. 自托管开放权重：选定权重及 tokenizer，通过推理服务提供 API。模型卡中的 chat template、stop token 和角色格式必须对应。开放权重仍有硬件、部署与许可成本。[31–33]

针对我们的 Netlify 网站，建议浏览器只调用自己的聊天接口，接口在服务端读取角色与会话，再请求模型并流式返回。密钥放服务端环境变量；共享网站需要限流与用量预算，否则任意访客都能产生费用。Netlify 托管网页不等于它能承载大模型 GPU 推理；自托管模型需要独立推理服务。具体函数超时和流式能力应在实施时再核实。

建议最少持久化：users、characters、character_versions、conversations、messages、memory_items、scene_states、feedback、generation_runs。每次生成记录模型版本、角色卡版本、提示词版本、检索条目 ID、输入输出 tokens、延迟和错误；实验日志不记录 API 密钥。

建议运行顺序：读取当前分支 → 加载角色与用户设定 → 检索有效记忆 → 按预算编译上下文 → 生成并展示 → 用户接受回复 → 提取事实与状态变化 → 写回该分支。不要在用户尚未选定回复时，把所有重生成候选都当成真实发生过的事件。

## 角色卡：最有价值的资源文件

Character Card V2 规定 JSON 包装与字段；PNG 可以携带角色数据，而不只是头像。V3 扩展资源，并提供 CHARX 打包方式。CHARX 是含根目录 card.json 的 ZIP，可包含媒体；规范允许字段不代表每个客户端都实现了对应功能。[34–35]

| 文件 / 字段 | 真正用途 | 我们如何使用 |
|---|---|---|
| description / personality | 身份、稳定性格、动机与行为 | 少写空泛形容词，多写触发条件与反应 |
| scenario | 开始时的世界与关系 | 与运行中的 scene_state 分开 |
| first_mes | 首轮声音、视角、篇幅和邀请用户行动 | 为短聊、剧情、慢热分别写开场 |
| mes_example | 展示该角色具体如何说话和选择 | 包含拒绝、冲突、误解修复；不能只示范甜言蜜语 |
| system_prompt | 卡作者希望模型遵守的生成规则 | 平台自己的系统规则仍独立管理 |
| post_history_instructions | 靠近历史末尾的提醒 | 用于当前场景约束，不堆重复规则 |
| character_book | 角色关联的世界书 | 大背景按需注入，身份核心保持稳定 |
| alternate_greetings | 不同开场 | 对不同初始关系明确标注 |
| 生成预设 JSON | 提示顺序、采样、接口配置 | 不同模型分别版本化 |
| 聊天 JSONL | 消息、分支和实际反馈 | 经过授权与筛选才进入训练候选集 |

Character.AI 的官方 Definition 文档也强调示例对话，并提醒长定义尾部可能被截断。写一个链接不会让模型自动读取该网页。[15]

针对原创角色，建议先写：当下目标、害怕失去什么、价值冲突、秘密及谁知道、对不同人物的不同态度、典型用词、避用表达。用行为检验“傲慢但有责任感”：面对公开羞辱会反击，但队友遇险时会先救人；这比把傲慢、善良、自信三个词并排更容易评估。

社区对 W++、自然语言、YAML、标签格式有争议。不能宣布某格式普遍最好。我们应以简洁自然语言或字段化描述为起点，保持内容相同做对照；真正变量是信息质量、token 成本、位置和模型适配。[40–42]

## 提示词组装与采样

SillyTavern Prompt Manager 公开了提示段、顺序、消息角色和插入深度；其默认 JSON 能直接查看标准配置。Chub 同样公开了 personality、scenario、memory、example_dialogue 等宏。[2,8,14]

我们的候选上下文：平台行为规则 → 角色核心 → 用户 persona → 稳定世界规则 → 已确认关系与事实 → 当前场景 → 少量相关旧事件 → 声音与行为示例 → 最近历史 → 当轮任务。此顺序只是待测试初版，不能假设所有模型都同样服从。

预算公式：输入上限 = 模型上下文上限 − 输出预留 − 提供方额外开销。先保住身份核心、当前消息、关键状态，再选择历史和世界书；不要机械保留所有描述。中文 token 数用实际 tokenizer 或 API 返回量统计，不用字数替代。

温度、top_p、min_p、重复惩罚等参数影响采样，不负责记忆。先用模型作者推荐值建基线，再一次改变一个变量。Euryale v2.3 作者推荐了其 Llama 模板与一组温度/min_p 设置，但不能照抄到闭源 API 或另一模型。[32]

回复长度需要“希望写多长”的提示和“允许输出多少”的预算共同控制。仅降低 max_tokens 可能使一句话中途截断，而不是使文风自然简洁。先排查模板、stop token、历史重复和开场篇幅，再调惩罚。固定 HUD 若每轮放在开头，OOC 帮助页提示可能加重重复。[25]

## 记忆与剧情：比长上下文更细的设计

世界书主要回答“世界本来是什么”；会话记忆回答“这个分支已经发生过什么”；场景状态回答“现在是什么情况”。三者不混成一段无限增长的摘要。

| 层 | 内容 | 更新方式 | 常见失败 |
|---|---|---|---|
| 角色核心 | 身份、价值观、底线 | 作者版本化 | 历史挤掉人设 |
| 世界书 | 地点、组织、设定 | 关键词或语义触发 | 未命中别名；递归条目膨胀 |
| 确认事实 | 承诺、偏好、已知秘密 | 提取后留证据、允许纠错 | 猜测被写成永久事实 |
| 事件记忆 | 重要结果、时间、参与者 | 按事件追加 | 时间顺序与分支混淆 |
| 临时摘要 | 最近发生的事情 | 接近窗口预算时压缩 | 摘要反复压缩发生变形 |
| 当前状态 | 地点、在场人物、目标、关系 | 接受回复后更新 | 关系突然升级、人物瞬移 |

SillyTavern/Chub 世界书明确使用触发条件、scan depth、token budget；不要把所有世界书称为向量数据库。[3,13] SillyTavern 另有聊天向量检索与 Data Bank，并明确提醒向量化不保证改善体验。其摘要还支持编辑和回退。[4–6]

OOC 帮助页公开四类记忆：Long-term、Temporary、Relationships、Goal。Character.AI 公开 Story Memory、可编辑 Facts 和 Memory Usage；这些是产品证据，实际检索算法未因此公开。[16,25]

建议记忆字段：id、conversation_id、branch_id、kind、subject、fact、event_time、source_message_ids、confidence、status、supersedes。状态至少区分 confirmed、proposed、retracted。关系事实带参与者；秘密带“哪些角色知道”；修正年龄等事实要废弃旧值。

检索候选分数可以综合相关性、人物匹配、时序、新近程度及重要性，再按预算选取。这是设计提议。保留稳定前缀，把动态内容放在后部，有助于减少前缀频繁改变；缓存收益仍取决于提供方。SillyTavern 当前的聊天向量化会重排上下文，文档指出会影响缓存命中。[5]

## 真正训练：有哪些公开材料

| 材料 | 方法与能取得的资源 | 对我们的价值 |
|---|---|---|
| ChatHaruhi [36] | 角色系统提示、故事文本与角色聊天实现 | 中文及动漫角色风格；查看怎样提供角色材料 |
| RoleLLM / RoleBench [37] | 角色画像、知识与风格数据生成、角色条件训练；作者发布数据 | 区分“知道角色的事”与“说得像角色” |
| Character-LLM [38] | 重建人物经历，再训练角色；公开数据和历史权重差分 | 用多样经历表现人格；老底模不作为今天默认部署选择 |
| Ditto [39] | 自生成角色数据后自对齐；WikiRoleEval 多轮测试输入 | 原创角色训练与角色知识边界评测 |
| CharacterGLM [45] | 中文属性与行为设计、对话训练和人工比较 | 中文评测维度；公开 6B 材料有研究使用限制 |
| character_AI_open [46] | 人设生成、多轮对话生成、去重与中文数据链接 | 小规模合成数据管线；作者指出熟悉角色偏差 |
| PIPPA [47] | 角色对话数据入口，当前标签 Apache-2.0 | 学习数据结构；不能直接把杂乱对话全部用于训练 |
| CoSER [48] | 文学角色数据、场景、经历、内心及训练评测框架 | 增加场景和多角色行为；论文结果限于其评测设定 |

SFT 学习优质示例的行为模式；LoRA/QLoRA 是降低训练资源需求的方法，不是保证质量的算法。DPO 使用相同输入下 preferred/rejected 两个输出，学习偏好方向；TRL 文档提供 prompt/chosen/rejected 结构。[49–50]

Character.AI 的历史 Kaiju 博客明确公开 SFT、基于用户 swipe 和反馈的 modified online DPO，以及分类器和推理优化。这说明真实用户的回复选择可以成为训练信号，但不证明每个角色都有独立模型，也不证明平台现在完全沿用历史方案。[17]

训练前应该积累“同一情境下角色应如何选择”的数据：拒绝与犹豫、信任建立、被纠正、冲突、关系改变、信息未知、计划受阻。全是表白或礼貌回答，会把不同角色拉向同一种讨好风格。合成数据必须人工抽检；生成教师模型的表达和价值倾向可能泄漏到所有角色。[46]

不要用我们的测试题生成训练集。按角色、场景和对话来源划分训练 / 验证 / 留出测试；已知角色测试与没见过的原创角色测试分别报告。模型权重许可、数据集许可、原著与角色素材使用权、合成数据提供方条款是不同问题，不能用代码仓库许可覆盖全部材料。

## 候选模型：资料充分不等于已经推荐部署

| 对象 | 已查材料 | 当前定位 |
|---|---|---|
| 厂商通用 API 模型 | OpenRouter 多轮与流式文档 [30] | 首轮对照组；具体型号实施时按可用性选择 |
| Pygmalion-3-12B | Mistral Nemo 基础、ChatML、角色对话/写作训练、Apache-2.0 模型卡 [31] | 开放权重候选；中文和长聊须实测 |

开放权重、有源码、公开训练数据、允许商用是四件事。某作者公开 Axolotl 配置也不表示其 datasets 路径对应的数据可下载。量化文件还要核对来源、模板和精度变化。

## 评测：怎样知道调得更像角色

InCharacter 用心理访谈评估人格忠实度；Ditto 的 WikiRoleEval 检验角色身份、知识及知识边界；RP-Bench 提供用户自主权、人物一致性、世界书利用等维度和可运行多轮种子。[39,51–52] RP-Bench 自己提醒 AI 评委和用户偏好可能分歧，因此不以单一自动评分选模型。CHAI 的研究说明互动指标能用于生产反馈，但会话长度只能作为代理指标。[29]

建议我们做 6 个原创角色 × 4 种场景 × 20 轮的第一轮实验；这是建议规模，不是行业标准。角色至少覆盖：冷淡有原则、热情但不讨好、谨慎谋略型、冲动行动型、喜剧型、严肃叙事型。场景覆盖日常、冲突、秘密和长剧情。

按同一份角色内容比较：A 简洁角色卡；B 加声音/行为示例；C 再加分层记忆。三种不同模型先使用相同条件，避免把换模型和换提示词的效果混在一起。记录模型更新与路由版本。

| 维度 | 观察问题 |
|---|---|
| 人物声音 | 去掉名字后是否还能辨认角色 |
| 动机与人格 | 利益冲突时是否仍体现价值选择 |
| 用户自主权 | 是否替玩家说话、行动或决定情绪 |
| 记忆 | 能否回忆约定并接受事实修正 |
| 知识边界 | 是否把秘密或未来事件当成已知 |
| 关系节奏 | 是否无缘由快速变亲密或改变立场 |
| 剧情推进 | 是否产生可回应的新行动而非每轮追问 |
| 连续性 | 时间、地点、物品和在场角色是否一致 |
| 表达 | 重复、套话、长篇堆词、格式泄漏 |
| 工程质量 | 首字延迟、完整回复延迟、token 成本、失败率 |

人工盲测同时看单句与完整多轮；评委模型只作辅助。偏好数据要记录为何选择：声音更像、记忆准确、节奏合适、或仅仅更长。反馈区分“没兴趣”与“生成失败”。

## 我们之后优先讨论的选择

1. 产品核心是“跟一个人聊天”还是“参与一个故事”。两者的旁白量、主动推进、状态与评测不同。
2. 目标语言以中文为主还是双语。英文 RP 模型卡不能证明中文人物自然。
3. 希望角色有自主立场到什么程度：会拒绝、犹豫、误解和保留秘密，还是始终配合用户。
4. 长期记忆是否跨会话复制、是否让用户编辑、重新生成和分支后如何回滚。
5. 先把模型 API、提示编译与记忆分开，实现可以替换的接口；收集失败样本后才决定 SFT 或 DPO。

资料包附原创研究用角色卡、记忆状态模板、评测用例和训练数据结构示例。它们未经过真实模型验证，不是已完成的“最佳 prompt”，也没有接到线上网站。
